# BUG-006: server integration test waits longer than its own Vitest timeout (flaky under CPU load)

- **Severity:** minor (test flakiness; product unaffected).
- **Build:** working tree 2026-11-18.
- **Suspected owner:** network-engineer (`server/server.integration.test.ts`, `server/transport.test.ts`).

## Steps to reproduce
1. `npx vitest run --reporter=verbose` while another CPU-heavy job runs (other agents' vitest/playwright).
2. Look at `server/server.integration.test.ts` "two clients join, get welcome + snapshots, and the match reaches
   playing" (no explicit timeout, so Vitest's 5000 ms default applies).

## Expected
Wall-clock socket tests have a test timeout comfortably above their own internal waits.

## Actual
- Idle machine: the test takes 2525 ms (no lag) and 2745 ms (100 ms RTT + 20 ms jitter) of real time (measured
  2026-11-18 08:49, `vitest-run1`).
- Inside it, `driveInputs(..., 2500)` runs 2.5 s and `waitFor(playingSnap, 6000)` may wait 6 s, both longer than or
  close to the 5 s default. Under load the test fails with "Test timed out in 5000ms" instead of its own message.
- `server/transport.test.ts` "join -> welcome -> playing ..." is the same pattern at 1.4-1.8 s.
- This matches the one unidentified failure seen "while other agents were busy". Not reproduced in 3 later full runs
  on a quieter machine (see docs/qa/M2a-test-report.md "Flakiness").

## Suggested fix
Pass an explicit timeout (e.g. `}, 20_000)`) to the wall-clock tests in both files, as QA did for
`tests/integration/pvp-over-ws.test.ts` (cheating-client tests now have 15-20 s).

## Evidence
`docs/qa/M2a-test-report.md` "Flakiness"; slow-test list from `npx vitest run --reporter=verbose`.

## Status: closed (fixed), 2026-11-18, M2b Phase D
Verified: `server/server.integration.test.ts` now gives every wait its own timeout inside the test's Vitest timeout
(header comment "BUG-006", `T = { wait: 8000, match: 20_000, test: 45_000 }`). Two full `npx vitest run` passes in
this round: 87 files, 1676 passed, 0 failed. One earlier run in this round had "deep link: hello and joinRoom
{ code } sent back to back" time out after 8000 ms (100 ms RTT variant) while other agents were also running test
jobs; it did not recur in the next two full runs, and the timeout now names the wait instead of hitting Vitest's
limit, which is what this bug asked for.
